1. Overview

Oracle Service Bus up to 12.1.3 has no native OAuth2/JWT support, and from 12.2.1 the OWSM policies cover it only partially and with little flexibility toward third-party identity providers such as Microsoft Entra ID. This project extends WebLogic with two custom security providers that bring OAuth2 bearer-token security to OSB in both directions:

ProviderWebLogic typeDirectionWhat it does
CustomInboundAuthenticator (CIA)Identity Asserter (IdentityAsserterV2)Consumer → proxy serviceValidates the JWT bearer token (or Basic credentials) presented to a proxy service and asserts the corresponding WebLogic realm user.
CustomOutboundAuthenticator (COA)Authentication provider + OSB OutboundAuthenticationBusiness service → backendObtains an access token from the identity provider (client credentials with secret or signed client assertion), caches it and sets Authorization: Bearer plus optional custom/secret headers on the outgoing HTTP request.

This project (osb-jwt-providers) is the evolution of osb-jwt-provider, which offered only the inbound identity asserter. Because the differences are radical, it is published in a new repository and its release numbering starts again from 1.0; from now on the package and each provider are versioned independently (§13.9). It replaces the configuration model of the old project (one large set of MBean attributes) with declarative XML policies stored as OSB resources: the MBean keeps only technical settings and the paths of those resources. The main changes compared with osb-jwt-provider:

  • The inbound provider is now driven by InboundPolicies.xml: trusted issuers, providers (JWKS URL and key cache), audiences, profiles and enabled identities. The old JWT_KEYS_*, JWT_IDENTITY_* and VALIDATION_ASSERTION attributes are gone.
  • A new outbound provider supports OAuth2 client credentials flows, per endpoint/project/profile policies, request and assertion templates, a token cache and custom or secret headers.
  • All client identifiers (client_id, resource and audience GUIDs) live in a single ResourceMappings.xml addressed by logical names; only secrets stay in OSB service accounts.
  • Every XML resource is validated against the XSD it declares, with caching of the positive outcome.
  • Inbound JWT verification pins the algorithm to RS256 and checks issuer, signature, expiry and audience.

Tested targets: Oracle Service Bus / WebLogic 12.2.1.4 (JDK 8) and 14.1.2 (JDK 17), one code base cross-compiled with Ant. WebLogic 12.1.3 is no longer supported: installations still on 12.1.3 can keep using release 1.1.0 of osb-jwt-provider. Identity providers used in tests: Microsoft Entra ID (token API v1 and v2) and Keycloak.

2. Architecture

  • Inbound: the proxy service uses HTTP transport with Custom Authentication. OSB extracts the configured header (normally Authorization) and calls assertIdentity() of the identity asserter registered for the token type. The returned user name becomes the security principal of the pipeline, so all the usual WebLogic tools (users, groups, roles, access policies on proxy services) keep working.
  • Outbound: the business service uses HTTP transport with Custom Authentication and the class org.falpi.osb.security.providers.CustomOutboundAuthenticator. OSB instantiates that class once per business service and calls doOutboundAuthentication() just before sending each request. The configured instance in the realm supplies MBean settings and caches to these per-service instances (see §2.1).
  • Configuration: XML resources and mapping service accounts live in an ordinary OSB project (in this code base the OAUTH2 project) and are read at runtime through the OSB configuration API, so they are deployed, versioned and promoted like any other OSB artefact and can be changed without restarting the server.

2.1 Why the outbound provider is a WebLogic security provider

WebLogic security providers are normally used to implement inbound security mechanisms. The outbound provider uses the same infrastructure for a different purpose. For business services with Custom Authentication the OSB HTTP transport only needs a class implementing com.bea.wli.sb.transports.http.OutboundAuthentication: OSB instantiates it by name and provides no configuration mechanism. Rather than building one (property files, a custom console, OSB resources for technical settings), the same class is also registered as a WebLogic authentication provider (AuthenticationProviderV2) with its own MBean definition, which gives it the standard capabilities of WebLogic and of its console:

  • typed attributes with defaults, legal values and descriptions, edited in the console (Provider Specific tab) and available through WLST and JMX;
  • persistence in config.xml under the domain change management (Lock & Edit, Activate), the same configuration on every server of the domain, dynamic attributes read again at every request;
  • a lifecycle managed by the server (initialize at boot, shutdown) and access to realm and domain services (realm, domain and server names, domain encryption used by ENCRYPTION_HELPER);
  • one instance per server that holds the caches shared by the per-business-service instances (access tokens, signing keys, OSB resources).

The provider never takes part in authentication: getLoginModuleConfiguration(), getAssertionModuleConfiguration(), getIdentityAsserter() and getPrincipalValidator() return null (CustomOutboundAuthenticator.java:149-166), so its position and control flag in the realm are irrelevant. The instances created by OSB for each business service borrow parameters and caches from the realm instance through a static registry, which is why exactly one outbound provider is allowed (§12).

3. Installation

3.1 Deploy the provider jar

The build (see §13.4) produces deploy/osb-jwt-providers-1.0.0.<yyyyMMdd>-fmw_<version>.jar and copies it as osb-jwt-providers-1.0.0.jar into

<WEBLOGIC_HOME>/wlserver/server/lib/mbeantypes

of the WebLogic installation of the selected target. On a server installation copy the same jar into that folder on every machine of the domain while the servers are stopped. By default the jar also contains osb-commons and its third-party libraries (mergeLibraries=true), so it is the only file to install. A build with mergeLibraries=false keeps the library in a separate file: then copy also the osb-commons jar of the same target (osb-commons-<version>-fmw_<target>.jar, the one taken by the build from lib/) into the same folder, once; the build does not copy it.

Keep exactly one copy of every class in mbeantypes: one osb-jwt-providers-*.jar and, only with a separate build, one osb-commons jar. WebLogic loads all the jars of mbeantypes (weblogic.descriptor.DescriptorClassLoader collects them in a HashSet) in a single class loader whose search order depends on the file names, not on the jar a class comes from: two copies of the same classes (two osb-commons versions, or an osb-commons jar next to a package built with merged libraries) are resolved unpredictably and can make the realm fail at boot with errors such as NoSuchFieldError or NoSuchMethodError. Before copying the new jar the deploy target removes from mbeantypes the previous osb-jwt-providers-* jars, the jars of the earlier project osb-jwt-provider (osb-jwt-provider-*) and, with merged libraries, the separate osb-commons-* jars; on the servers of the domain remove them by hand (see the README for domains that still use osb-jwt-provider).

3.2 Create the providers in the realm

After restarting, open Security Realms → myrealm → Providers → Authentication in the WebLogic console and create the two providers with New.

  • Inbound: type CustomInboundAuthenticator. Use Reorder to move it to the top of the list, as for any identity asserter that must handle a header before the default ones. More than one inbound instance may exist (e.g. with different policy files); the token types with suffix #1/#2 let each proxy select which instance asserts its tokens.
  • Outbound: type CustomOutboundAuthenticator. Exactly one instance is allowed: a second one makes the server fail at boot (see §12 and §14.3). The provider takes no part in user logins (it returns no login module), so its position and control flag are not relevant; leave the control flag at OPTIONAL.

Then open each provider, tab Configuration → Provider Specific, set the parameters (§7.2 and §8.2), save and activate the changes. The attributes are shown in the same order as in the MBean definition files thanks to a customised BeanInfo generated from a patched MBeanMaker template (§13.4).

Most attributes are dynamic: their value is read again at every request, so changes in the console take effect without restart. KERBEROS_CONFIGURATION is read only at initialization.

3.3 Make the outbound class visible to OSB (setDomainEnv)

The jars of mbeantypes are loaded by the security provider class loader, which OSB does not use: the HTTP transport of a business service with Custom Authentication loads the class named in its configuration from the server classpath. The Oracle documentation on custom outbound authentication does not explain this step; as indicated by Oracle support, the provider package (and osb-commons, when built separately) must be added to the server classpath in <DOMAIN_HOME>/bin/setDomainEnv.cmd (setDomainEnv.sh on Linux/Unix), in the assignment of POST_CLASSPATH that contains servicebus-common.jar:

set POST_CLASSPATH=<WEBLOGIC_HOME>\osb\lib\servicebus-common.jar;<WEBLOGIC_HOME>\wlserver\server\lib\mbeantypes\osb-jwt-providers-<packageVersion>.jar;%POST_CLASSPATH%

With a separate osb-commons jar (mergeLibraries=false) list it as well:

set POST_CLASSPATH=<WEBLOGIC_HOME>\osb\lib\servicebus-common.jar;<WEBLOGIC_HOME>\wlserver\server\lib\mbeantypes\osb-commons-<version>-fmw_<target>.jar;<WEBLOGIC_HOME>\wlserver\server\lib\mbeantypes\osb-jwt-providers-<packageVersion>.jar;%POST_CLASSPATH%
  • Reference the same files copied into mbeantypes (§3.1). The deploy target copies the package with the stable name osb-jwt-providers-<packageVersion>.jar, so the entry changes only with the package or osb-commons version; a dated jar copied by hand from deploy/ must be referenced with its exact name, and a later build replaces it with the stable name.
  • Only the outbound provider needs it; the inbound provider is loaded from mbeantypes only.
  • Apply it on every machine of the domain and restart; servers not started through the domain scripts need the same entries in the class path of their server start configuration. In the JDeveloper integrated domain the script is in %APPDATA%\JDeveloper\system<version>\DefaultDomain\bin.
  • Classes on the server classpath are found before those of mbeantypes (the provider class loader delegates to its parent first): with the entries above, the classes of the package and of osb-commons are always taken from those files, also by the providers loaded from mbeantypes.

The resources consumed at runtime are ordinary OSB resources. The recommended layout, used by the sample project osb/OAUTH2:

OSB resource paths are written <project>/<folder>/.../<resource>, without extension. Proxy server resources always live in System/Proxy Servers/<name>. All path attributes of the MBeans accept template variables, e.g. ${osb.project}/Security/HeaderSecrets to keep secrets per project (exception: outbound JWT_POLICIES_PATH, read verbatim).

Sample project. The folder osb/OAUTH2 contains a complete JDeveloper/OSB project with every resource of the table and a consistent configuration: two IDPs (Entra ID and Keycloak), inbound issuers, profiles and identities, outbound defaults, profiles, project and endpoint policies (including a secure header keyed by service and operation), templates, client keys and both secret stores. Names and values are fictitious, keys and secrets are placeholders; all the XML files validate against the schemas. The examples of this guide are taken from it.

Resources are read through OSBUtils.getResourceCached: the parsed document is kept in memory and reloaded only when the OSB last change time of the resource changes, so a deployment of a new version is picked up at the next request.

5. XML validation

Every XML resource is loaded with CustomAuthenticator.validateResource() (CustomAuthenticator.java:558):

  1. The root element must declare xsi:noNamespaceSchemaLocation. Its value is resolved as an OSB path: absolute if it starts with /, otherwise relative to the folder of the XML resource; ., .. and a trailing .xsd are handled. Example: OAUTH2/Security/InboundPolicies + ../Schemas/InboundPolicies.xsd → OAUTH2/Schemas/InboundPolicies. URL locations (http:, file:…) are rejected.
  2. The footprint xml change time | schema path | schema change time is compared with the last positive outcome; if equal the resource is returned immediately.
  3. Otherwise the schema text is read from the OSB schema repository and the resource is validated with XmlBeans (XMLUtils.validate), including xsd:key/xsd:keyref/xsd:unique constraints.

Two modes exist (validateResource(path, BolException)). All current calls use the default (false): validation errors are logged at ERROR level, one line per error, and the resource is still used, so a small mistake does not stop the traffic. A missing resource always raises an exception. Negative outcomes are not cached: an invalid resource is validated (and logged) again at every request until it is fixed.

JDeveloper validates the same XML files at design time with the Oracle XDK. If an XSD is changed outside JDeveloper, refresh the schema in the IDE; at runtime the XSD deployed on OSB is used, so deploy XML and XSD together.

6. Resource mappings and naming

ResourceMappings.xml centralises every identifier that is not a secret, so it can be read in clear from the OSB console and reused by inbound and outbound:

<resourceMappings xsi:noNamespaceSchemaLocation="../Schemas/ResourceMappings.xsd" ...>
   <provider name="azure">
      <item name="consumer-a"       value="<client_id of consumer A>"/>
      <item name="esb-to-backend-x" value="<client_id used by the ESB toward backend X>"/>
      <item name="esb-api"          value="<Application ID URI or client_id of the ESB API>"/>
      <item name="function-a"       value="<resource id of Function App A>" note="free text"/>
   </provider>
</resourceMappings>

Two lookups are available in the base class:

  • translateResource(mappings, provider, name) – name → value (XPath on configuration data; exactly one match required, otherwise invalid resource mapping (provider:name)).
  • reverseTranslateResource(mappings, provider, value) – value → name. The value can come from a token, so items are compared in Java; zero matches gives unmapped value, more than one ambiguous resource mapping.

Provider names and logical names are free text chosen by the administrator: the providers only require them to be consistent across the files. All the names used in the examples (identities, users, projects, services, operations) are fictitious; a naming convention, for example prefixes that distinguish app registrations, APIs and Function Apps, can be adopted but is not required.

7. Inbound provider (CustomInboundAuthenticator)

7.1 Token types and proxy service setup

The provider declares the token types CIA.BASIC, CIA.JWT, CIA.JWT+BASIC and their variants with suffix #1 and #2. Select the active ones in Configuration → Common → Active Types.

CIA.JWT+BASIC accepts both schemes on the same proxy, which allows a progressive migration of consumers from Basic to OAuth2. The suffixes allow several provider instances, each activating its own types.

On the proxy service (JDeveloper or OSB console), Transport Details: Authentication = Custom Authentication, Authentication Header = Authorization (mandatory when Basic must be accepted too), Authentication Token Type = one of the active types.

The header value is inspected as follows (CustomInboundAuthenticator.java:315-336): a value starting with Basic  is Basic authentication; anything else is a JWT, with an optional Bearer  prefix removed. The detected scheme must be part of the selected token type and enabled by BASIC_AUTH / JWT_AUTH, otherwise the request fails with Token preparation error.

7.4 Processing flow

  1. Parse the compact JWT with Nimbus (prepareToken). Header kid and payload iss are read but not trusted yet. A token without iss is rejected immediately.
  2. Issuer: the issuer item whose issuerURL equals iss is searched by comparing strings in Java. It gives provider and identity claim; the provider item gives JWKS URL and key cache TTL.
  3. Mappings: ResourceMappings is loaded and kept in the request context.
  4. Key: prepareKey(kid) returns the cached RSA key jwksURL#kid or downloads the JWKS and keeps only the requested key (kty=RSA, use absent or sig).
  5. Verify: the header alg must be RS256; then Nimbus verifies the signature and requires valid exp and nbf claims (60 s clock skew).
  6. client_id → identity: the value of the identity claim (any JSON type, converted to string) is reverse-translated through ResourceMappings of the provider.
  7. Enabled identity: the identity must be listed under identities/provider[@name]; the item gives the realm username and the optional profile. A client mapped in ResourceMappings but not listed (e.g. an outbound identity) is rejected.
  8. Audience: the profile audience (or the provider audience) is translated through ResourceMappings and must be equal to aud or contained in it when aud is an array.
  9. Assert: custom request/response headers and debugging properties are processed, the INFO line is logged and a CallbackHandler returning username is given to WebLogic, which then runs the authenticators' principal validation for that user.

Context variables set during the flow and usable in templates: authtype, provider, identity_claim, jwks_url, keys_cache_ttl, client_id, identity, username, profile, audience, and the token itself through ${token.*}.

With Entra ID, v1 tokens carry iss=https://sts.windows.net/<tenant>/ and the client in appid; v2 tokens carry iss=https://login.microsoftonline.com/<tenant>/v2.0 and the client in azp. Configure one issuer item for each version you accept. The value of aud is the resource as requested by the client (GUID or Application ID URI): the mapped audience must contain exactly that form.

7.5 Basic authentication

With CIA.BASIC or CIA.JWT+BASIC and BASIC_AUTH=ENABLE, user:password is decoded and checked with the WebLogic embedded LDAP authenticator (WLSUtils.getAuthenticator, class EmbeddedLDAPAtnDelegate). The authenticated user name is asserted; the policies are not used. Users defined only in other authenticators (LDAP, Active Directory) cannot log in through this path.

7.6 Signing keys (JWKS)

The JWKS is fetched with HTTP GET, Accept JSON, through the proxy and TLS settings of the MBean. The cache key is jwksURL#kid, so providers sharing a kid do not collide. Only the requested key is stored; a token with an unknown kid triggers a download every time. Microsoft rotates its signing keys periodically: a TTL of one hour is a good compromise.

8. Outbound provider (CustomOutboundAuthenticator)

8.1 Business service setup

On the business service, Transport Details: Authentication = Custom Authentication, HTTP Custom Authentication Class Name = org.falpi.osb.security.providers.CustomOutboundAuthenticator. Do not associate a service account: the provider rejects it with Service Account not allowed.

OSB loads the class from the server classpath and requires it to implement OutboundAuthentication (see the Oracle documentation on custom outbound authentication). The jar in mbeantypes is not enough: the package (and osb-commons, when built separately) must also be listed in POST_CLASSPATH of setDomainEnv (§3.3). The realm provider must exist, otherwise each call fails with Custom Outbound provider not configured in security realm.

      <item name="function-keys" identity="esb-to-${osb.project}" method="secret"
            secureHeader="x-function-key:${osb.service.name}-${osb.operation}" />
   </profiles>

   <!-- changes for all the business services of an OSB project -->
   <projects>
      <item name="ProjectA" profile="function-keys" resource="function-a" />
      <item name="ProjectB" profile="secret-auth" />
   </projects>

   <!-- changes for a single business service -->
   <endpoints>
      <item name="BS_Orders_1.0" resource="function-b">
         <customHeader name="x-correlation-id" value="${uuid}" />
      </item>
      <item name="BS_BackendX_1.0" identity="esb-to-backend-x" method="assertion" resource="backend-x-api" />
      <item name="BS_Inventory_1.0" provider="keycloak" identity="esb-keycloak" method="assertion" assertion_request="keycloak"
            resource="" resource_mapped="false" />
   </endpoints>

</outboundPolicies>

Levels and precedence

Four levels can define the same attributes: defaults (all attributes required), profiles/item, projects/item (matched on the OSB project of the business service) and endpoints/item (matched on the local name of the business service or on its full path project/folders/name; when both forms exist the full path prevails, so business services with the same name in different projects can be told apart). The matched item is logged at DEBUG as Endpoint Policy. A project or endpoint may reference one profile; if the endpoint declares a profile, the profile of the project is ignored. The profile sits right after the level that declares it.

   <token name="standard" type="client_assertion">
      <claim name="iss" type="String">${client_id}</claim>
      <claim name="sub" type="String">${client_id}</claim>
      <claim name="aud" type="String">${token_url}</claim>
      <claim name="iat" type="Integer">${current.epoch}</claim>

      <claim name="jti" type="String">${uuid}</claim>
   </token>
   <request name="azure-token-v1" method="secret" tokenURL="https://login.microsoftonline.com/<tenant>/oauth2/token">
      <parameter name="grant_type"    type="String">client_credentials</parameter>
      <parameter name="client_id"     type="String">${client_id}</parameter>
      <parameter name="client_secret" type="String">${client_secret}</parameter>
      <parameter name="resource"      type="String">${resource}</parameter>
   </request>
   <request name="azure-token-v2" method="assertion" tokenURL="https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token">
      <parameter name="grant_type"            type="String">client_credentials</parameter>
      <parameter name="client_id"             type="String">${client_id}</parameter>
      <parameter name="client_assertion_type" type="String">urn:ietf:params:oauth:client-assertion-type:jwt-bearer</parameter>
      <parameter name="client_assertion"      type="String">${client_assertion}</parameter>
      <parameter name="scope"                 type="String">${scope}</parameter>
   </request>
</outboundTemplates>
  • A request (name + method unique) defines the token endpoint (tokenURL, exposed as ${token_url}) and the form parameters, sent URL-encoded with Content-Type: application/x-www-form-urlencoded. The JSON response must contain access_token.
  • A token (name + type unique, type client_assertion) defines the claims of the client assertion, signed with the key of the identity (header typ=JWT, kid when not empty).
  • Value types: String values are wrapped in quotes and evaluated (templates resolved first), so they are taken literally; Integer values are JavaScript expressions that must return an integer (e.g. ${current.epoch}+60). See §10.

8.5 ClientKeys.xml and the encryption helper

<clientKeys xsi:noNamespaceSchemaLocation="../Schemas/ClientKeys.xsd" ...>
<item provider="azure" identity="esb-to-backend-x" kid="<certificate thumbprint>" alg="RS256"
      password="encrypted:<base64>">
-----BEGIN ENCRYPTED PRIVATE KEY-----
...
-----END ENCRYPTED PRIVATE KEY-----
</item>
</clientKeys>
  • provider + identity is the key of the item (unique). The client_id comes from ResourceMappings, not from this file.
  • Supported PEM formats: PKCS#8 (BEGIN PRIVATE KEY, BEGIN ENCRYPTED PRIVATE KEY) and traditional OpenSSL (BEGIN RSA PRIVATE KEY, encrypted with DEK-Info or not). Encrypted keys require password, plain keys require it empty. Only the first PEM object is read.
  • alg: RS256 (the code also supports PS*/ES* but the XSD allows only RS256).
  • password: either clear text or encrypted:<base64> produced by the ENCRYPTION_HELPER attribute of the outbound provider: type the password there, save, and copy the stored value. The encryption uses the WebLogic domain key, so the value is valid only in that domain.

8.6 ClientSecrets and HeaderSecrets (mapping service accounts)

Both are OSB service accounts of type Mapping used as secure key/value stores: only Remote Users are read. The local user mappings can stay empty; an anonymous mapping (any remote user) avoids the editor complaint about an empty mapping list.

  • ClientSecrets: remote user name <provider>:<identity>, remote password = <client-secret>. The name is the plain concatenation of provider name, colon and identity name, compared as a whole (e.g. provider azure and identity esb-to-ProjectA give azure:esb-to-ProjectA).
  • HeaderSecrets: remote user name = the resolved key of a secure header, remote password = <header-value>. The key is a template, so a single policy can select a different secret for each service or operation: with secureHeader="x-function-key:${osb.service.name}-${osb.operation}" (the case of Azure Function Apps, where every function has its own key) a call to the operation createOrder of the Business Service BS_Orders_1.0 reads the remote user BS_Orders_1.0-createOrder. Any template variable can be combined (project, service, operation, metadata, ...), and a fixed key works as well.
Rename remote users by editing the .sa file: the JDeveloper service account editor resets the passwords of renamed rows. A .sa file that contains passwords encrypted for another domain ({AES256}…) makes JDeveloper Refresh Application fail with Invalid padding.

8.7 Processing flow

  1. Context: checks the realm provider and the absence of a service account, borrows the context of the realm instance, builds config and context, detects the operation (§8.8).
  2. Policies: selects the applicable levels, consolidates the attributes and the headers.
  3. Templates and mappings: request template for the method (plus token template for assertion) → ${token_url}; loads ResourceMappings.
  4. Authentication: resolves the identity templates, translates the identity into ${client_id}; method secret reads ${client_secret} from ClientSecrets (secret not found if missing); method assertion signs the token template with the ClientKeys item → ${client_assertion}.
  5. Authorization: resolves and translates resource, then resolves scope.
  6. Access token: computes the cache key; on a miss posts the request template to token_url, parses access_token and caches it.
  7. Headers: Authorization: Bearer <token>, MBean custom headers, policy headers (secure values from HeaderSecrets).
  8. Debugging properties and the INFO line; OSB then sends the request.

Context variables available in templates after each step: policy attributes (provider, identity, method, scope, resource, resource_mapped, secret_request, assertion_request, assertion_token, token_cache_ttl, token_cache_index), token_url, client_id, client_secret or client_assertion, and the access token through ${token.*}.

8.8 Operation detection

${osb.operation} (used for example in secure header keys) is resolved by detectOperation() in this order:

  1. From the pipeline message context reached through the sender (reflection on OSB internals): $outbound/ctx:service/ctx:operation via OutboundEndpoint.getServiceInfo().getOperation(), then $operation.
  2. When there is no pipeline (business service tested from the OSB console) or the context has no operation: for SOAP services with WSDL, the operation whose soapAction matches the SOAPAction header (SOAP 1.1) or the action parameter of the Content-Type (SOAP 1.2); if the binding has a single operation, that one.
  3. Otherwise an empty string.

${osb.operation.source} and ${osb.operation.message} tell which rule applied.

8.9 Access token cache

Tokens are cached in the realm instance under the resolved token_cache_index. An entry is discarded when now ≥ exp of the token or now ≥ cached time + token_cache_ttl. A token without exp counts as already expired, so it is used once and never reused. A TTL a few minutes shorter than the token lifetime (e.g. 3000 s for one-hour tokens) avoids sending tokens that expire in transit.

8.10 Faults returned by OSB

Errors are raised as TransportException with a short message; the detail is in the provider log. OSB turns it into fault OSB-380000 with the message as reason. When the token endpoint answers with an error and a JSON body, the error_description is appended to the message, e.g.

OSB-380000: General runtime error: Error while preparing access token (AADSTS7000215: Invalid client secret provided. ... Trace ID: ... Correlation ID: ...)

For transport errors other than OSB-380001 OSB applies the retry and failover settings of the business service, so a token error is retried like a connection error.

9. Template variables

Strings in MBean parameters, resource paths, policies and templates may contain ${name} placeholders, resolved by StringUtils.replaceTemplates:

  • Names are dot-separated segments of letters, _ and -, optionally ending with .*. Digits are not allowed: ${claim1} is a syntax error.
  • The value must be a string or a function; a missing variable (or one holding an object or null) raises invalid template variable. There is no default value syntax.
  • All occurrences are replaced; replacement is not recursive.

12. Threading, state and caches

  • Per-request state (logger, config snapshot of the MBean, context) is kept in ThreadLocals created at the start of each call and cleared at the end by cleanThread, called in a finally block so that the request objects, tokens and secrets never stay on the pooled thread, also after an error or an exception. WebLogic calls identity asserters and outbound authentication in parallel; THREADING_MODE=SERIAL serializes the calls of one instance.
  • Thread names: setThreadName() renames the executing thread to the 7-digit request counter of the instance, which appears in the log lines.
  • Instances: WebLogic creates one inbound instance per realm provider. For outbound, WebLogic creates the realm instance (with MBean and caches) and OSB creates one instance per business service; the first call of each borrows the provider context of the realm instance from a static registry (logged as Provider context init). A second outbound provider in the realm makes the server fail at boot: the provider throws ProviderInitializationException, the realm fails to load (BEA-090870) and the server goes to FAILED and shuts itself down (BEA-000383). shutdown() removes the realm instance from the registry, so a new initialize() in the same JVM is not taken for a second provider.
  • Caches (all in memory, per JVM): parsed OSB resources by change time (OSBUtils), positive validation outcomes (ObjValidationCache), JWKS keys (JWTCache.keysCache, by jwksURL#kid), access tokens (JWTCache.tokensCache, by cache index). Expired entries are removed when the same key is looked up again.

13.4 Build pipeline

Run build-1221.cmd or build-1412.cmd, or the all target from JDeveloper. Properties to adapt in build.xml (prepare target): javaHomeDir and weblogicDir for each target; options embedSources (default false) and mergeLibraries (default true, see §3.1).

    <switch value="${targetConfig}">
      <case value="12.2.1"> ... <property name="javaHomeDir" value="C:/Programmi/Java/jdk1.8"/>
                                 <property name="weblogicDir" value="C:/Oracle/Middleware/12.2.1"/> ...
      <case value="14.1.2"> ... jdk17  / C:/Oracle/Middleware/14.1.2 ...
  1. clean – removes build/.
  2. build.MTF – extracts BeanInfoBinder.template from the WebLogic beangen module and injects res/BeanInfoBinder-head.template and -body.template: the generated BeanInfo reorders the property descriptors following the MDF, so the console shows the attributes in the XML order (see below).
  3. build.MDF – WebLogicMBeanMaker generates the MBean interfaces and the Impl stubs from the MDF files.
  4. build.MJF – MBeanMaker generates MBeanImpl/BeanInfo/factory and builds build/osb-jwt-providers.jar.
  5. patch – injects WLSUtils.encryptionHelper at the beginning of the setter of ENCRYPTION_HELPER in CustomOutboundAuthenticatorMBeanImpl.
  6. rebuild – recompiles the patched sources and rebuilds the jar.
  7. deploy – creates deploy/osb-jwt-providers-1.0.0.<date>-fmw_<ver>.jar (merging lib/*-fmw_<ver>.jar when mergeLibraries=true, the default, otherwise osb-commons is installed separately; sources excluded unless embedSources=true), removes from mbeantypes the jars that would duplicate its classes (§3.1) and copies it to mbeantypes/osb-jwt-providers-1.0.0.jar (name and version from packageName / packageVersion, build.xml:142-143); the manifest records package and provider versions (§13.9). The user running the build needs write permission on mbeantypes (§15).

Console attribute ordering (template injection). The BeanInfo classes generated by MBeanMaker return the property descriptors in alphabetical order, so by default the console shows the provider attributes alphabetically, regardless of their order in the MDF. Since its first versions the project changes this behaviour by modifying the code generator itself. MBeanMaker builds the BeanInfo classes from internal code generation templates packaged in com.bea.core.beangen.jar; the one involved is weblogic/management/internal/mbean/BeanInfoBinder.template, written in the template language of the generator (expressions such as $class.getClassName()). The build.MTF target extracts that template into build/, under the same relative path, and injects res/BeanInfoBinder-head.template (additional imports, after the BeanInfoHelper import) and res/BeanInfoBinder-body.template (an override of getPropertyDescriptors(), after the bean descriptor method). MBeanMaker then runs with build/ as working directory and uses the patched template instead of the packaged one. The injected method builds the standard descriptors, reads at runtime the MDF packaged in the jar next to the class (its name is derived from the BeanInfo class name, so the same template serves every provider of the package) and returns Name and Realm first, followed by the attributes in the MDF order, dropping those that are not exposed as properties. Oracle does not document this mechanism: identifying the template, the injection points and the lookup of the patched copy required the reverse engineering of the MBeanMaker templating. A second, simpler customization patches the generated source of the ENCRYPTION_HELPER setter (patch and rebuild targets). If the reordering fails the error is only printed and the descriptors may be incomplete: see the issues document.

The osb-commons dependency is taken from lib/ by the pattern *-fmw_${weblogicVersion}.jar: build CommonLib for the same target first and copy its jar from CommonLib/deploy into lib/. The CommonLib build only produces the jar in CommonLib/deploy: by default it is merged into the provider package, otherwise it is installed once into mbeantypes (§3.1).

13.6 Coding rules

  • Sources are windows-1252 with CRLF line endings; comments are in Italian. Keep the encoding when editing (some editors convert to UTF-8 and corrupt accented characters).
  • Naming: Hungarian-like prefixes (Str, Int, Bol, Obj, Arr), Logger, Config, Context locals; sections delimited by banner comments.
  • Every step catches its exceptions, logs ERROR with the cause and rethrows the provider exception type (IdentityAssertionException / TransportException) with a short message.
  • Values coming from tokens or requests are never concatenated into XPath or script text: compare in Java.
  • Never log secrets above TRACE.

13.7 Extending the providers

  • New MBean attribute: add <MBeanAttribute> to the MDF (position = console order), a constant and a Config.put in createConfig(), log it in the CONFIGURATION block, validate it with validateParameter if mandatory. Rebuild with MBeanMaker (the interface getter is generated).
  • New outbound policy attribute: add it to abstractType (optional) and defaultType (required) of OutboundPolicies.xsd and to the list in preparePolicies() (line 538): it becomes a context variable automatically.
  • New template variable: Context.put(name, String) for static values, Context.put(name, TemplateFunction) for lazy values, Context.putRegex(regex, TemplateFunction) for parametric names. Names cannot contain digits.
  • New identity provider: no code change; add provider, issuers and identities (inbound), request templates and mappings (outbound).

13.8 Testing

  • Schemas and XML resources can be validated offline with both XmlBeans (runtime) and Oracle XDK (JDeveloper) using small Java harnesses (classpath: servicebus.jar, weblogic.jar, osb-commons; XDK: oracle_common/modules/oracle.xdk/xmlparserv2_sans_jaxp_services.jar).
  • The providers can be tested in the JDeveloper integrated domain: the build deploys the jar to its mbeantypes. Use the OSB test console on proxies (Authorization header) and business services (operation detected from SOAPAction).
  • LOGGING_LEVEL=TRACE and DEBUGGING_PROPERTIES such as ${token.payload.*} show the full context of a request.

13.9 Versioning and package manifest

Two independent levels of versioning are used, because the providers have their own development cycles while every release always ships both of them in one jar:

LevelDeclared inIdentifiesChange it
ProviderDefault of the read-only MBean attribute Version in CustomInboundAuthenticator.xml:36 and CustomOutboundAuthenticator.xml:36Code and MBean of that provider; shown in the console and in the Provider Title log line (Description (Version))When that provider changes
PackagepackageVersion, build.xml:143A release of the jar (both providers, osb-commons and libraries when merged); part of the jar nameAt every release, also for library or build changes

The package version is not computed from the provider versions (e.g. as their maximum): different releases could share a number and library-only releases would not change it. Suggested rule: major when a provider changes its major number or the configuration (MBean attributes, XSD) changes incompatibly, minor for new features, patch for everything else.

Runtime. CustomAuthenticator.getPackageTitle() (line 344) opens the jar given by the CodeSource of the class, reads the main attributes of its manifest and returns <title> <version> (<build date>, <build target>, legacy <version>, inbound <version>, outbound <version>); the jar is closed in a finally. Any failure (class not loaded from a jar, manifest without the attributes) gives unknown and never stops the initialization. init() stores the value in ProviderContext.packageTitle and logs it as Package Title right after Provider Title (§11.1). 14.3 Initialization (ProviderInitializationException → server FAILED)

Errors raised by init() and by the outbound initialize() are logged by the provider at ERROR level and thrown as weblogic.security.spi.ProviderInitializationException (unchecked, so the SSPI signature does not change). WebLogic reports them as BEA-090870 The realm "<realm>" failed to be loaded followed by BEA-000362 Server failed, FAILED state and BEA-000383 A critical service failed. The server will shut itself down. The message carries the provider name in brackets.
